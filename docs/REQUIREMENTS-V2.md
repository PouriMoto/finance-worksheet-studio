# نیازمندی‌های نسخه‌ی ۲ (ثبت‌شده از تصمیم‌های Pouria)

## ۱. تصمیم‌های ثبت‌شده
| # | تصمیم |
|---|---|
| R1 | فعلاً کودک نداریم؛ مکانیزم‌های آموزش کودکان فقط الهام برای **بزرگسال** (مد کودک حذف شد) |
| R2 | حساب شخصی با احراز هویت (auth) و صفحه‌ی پروفایل |
| R3 | هر بازی/کتابی که کاربر انجام می‌دهد در پروفایلش می‌نشیند؛ تاریخچه، نتیجه و گزارش‌ها قابل‌دیدن است |
| R4 | صفحه‌ی خانه مثل CrazyGames: شبکه‌ی کاشی بازی‌ها، انتخاب یک بازی ← صفحه‌ی همان بازی. مهمان هم بازی می‌کند؛ عضو ذخیره و پروفایل دارد |
| R5 | آرشیو جدا برای همه‌ی بازی‌ها و کتاب‌ها |
| R6 | اشتراک ماهانه؛ بعضی بازی/کتاب‌ها پولی، بعضی رایگان |
| R7 | اقتصاد توکن و امتیاز: اشتراک توکن می‌دهد تا تعداد مشخصی بازی/کتاب باز شود؛ بازی‌کردن امتیاز می‌دهد و با امتیاز مورد بیشتری باز می‌شود |
| R8 | کد تخفیف و تایمر کمپین تخفیف (مشخص و دوره‌ای) |
| R9 | دو نسخه: **Local** (بدون بک‌اند، داده در مرورگر) و **Cloud** (پولی/کامل‌تر، با بک‌اند). بک‌اند فعلاً PocketBase |

## ۲. دو نسخه از یک کدبیس
یک متغیر `PUBLIC_EDITION=local|cloud` تعیین می‌کند چه قابلیت‌هایی روشن باشند.

| قابلیت | Local | Cloud |
|---|---|---|
| بازی مهمان، استریک، XP، پروفایل رفتاری | ✅ localStorage | ✅ |
| حساب کاربری، ورود | ❌ | ✅ |
| همگام‌سازی بین دستگاه‌ها، تاریخچه‌ی کامل | ❌ (فقط خروجی/ورودی JSON) | ✅ |
| محتوای پولی، اشتراک، پرداخت | ❌ فقط محتوای رایگان در build | ✅ |
| توکن/امتیاز قابل‌اتکا، کد تخفیف، تایمر کمپین | ❌ | ✅ (سرور تصمیم می‌گیرد) |
| push/تلگرام، داشبورد آمار | ❌ | ✅ |

قواعد:
- Local: در build فقط پکیج‌های `access: free` وارد می‌شوند؛ پولی‌ها اصلاً در خروجی نیستند.
- Local: دکمه‌ی «دانلود پشتیبان» و «بازیابی» لازم است (پاک شدن مرورگر = از دست رفتن داده).
- یک `StorageAdapter` مشترک (`local`، `pocketbase`) و یک `EntitlementProvider` (`allFree`، `pocketbase`).

## ۳. نکته‌ی بحرانی: محتوای پولی نباید در بسته‌ی استاتیک باشد
الان داده‌ی هر پارت داخل HTML صفحه‌ی بازی گذاشته می‌شود؛ هر کسی می‌تواند محتوای پولی را بخواند.
راه‌حل پیشنهادی برای Cloud:
1. پارت‌های **رایگان** مثل الان استاتیک؛ پارت‌های **پولی** فقط در PocketBase (`part_content`) با API rule «کاربر دارای entitlement».
2. صفحه‌ی پلیر برای پارت پولی یک پوسته است و داده را هنگام بازی از API می‌گیرد.
3. اسکریپت `npm run publish:content` پارت‌های پولی را از git به PocketBase می‌فرستد (git همچنان منبع حقیقت).
4. پیش‌نمایش: پارت اول هر کتاب پولی رایگان باشد (پیشنهاد، قابل‌تغییر).
فیلدهای جدید `package.yaml`: `access: free | premium`، و در سطح پارت (اختیاری) `access` برای مدل «پارت اول رایگان».

## ۴. مدل داده‌ی PocketBase (طرح، وصل‌نشده)
- `users` (auth)، `profiles` (نمایش، تنظیمات، شناسه‌ی ناشناس مهمان)
- `sessions` (هر بار بازی: pkg, part, started, finished) و `part_results` (پاسخ‌ها + snapshot گزارش)
- `entitlements` (user, pkg|part, source: `sub|token|points|purchase|promo`, from, until)
- `plans`، `subscriptions`، `payments` (authority یکتا)
- `ledger` (دفتر امتیاز/توکن، **فقط‌افزودنی**، `idem_key` یکتا)
- `coupons`، `coupon_redemptions`، `campaigns`
- `events` (تحلیلی)، `part_content` (محتوای پولی)
قاعده: کلاینت فقط می‌خواند/پاسخ می‌فرستد؛ `ledger`، `entitlements`، `subscriptions`، قیمت‌ها و تخفیف را **فقط hookهای سرور** می‌نویسند.

## ۵. اقتصاد توکن/امتیاز (پیشنهاد پارامتری؛ عددها تصمیم تو)
- **توکن** (از اشتراک یا خرید): خرج‌کردن برای باز کردن یک مورد برای N روز یا همیشه.
- **امتیاز** (از بازی‌کردن): فقط برای اولین تکمیل هر پارت، با سقف روزانه؛ برای باز کردن موارد ارزان‌تر.
- ضد سوءاستفاده: امتیاز با تکرار همان پارت داده نمی‌شود؛ سقف روزانه؛ امتیاز به توکن تبدیل نمی‌شود؛ بازشدن با امتیاز موقت (مثلاً ۷ روزه)؛ همه‌ی محاسبه‌ها سمت سرور.
- پارامترها در `content/economy.yaml` (در git، سرور می‌خواند): دادن ماهانه، هزینه‌ی هر مورد، سقف روزانه.
- اشکال طراحی که باید پیش از ساخت رفع شود: «با امتیازی که از بازی‌های باز شده جمع می‌شود بازی‌های بیشتر باز می‌شود» اگر نرخ‌ها درست نباشد، اشتراک بی‌معنی می‌شود (کاربر بدون پرداخت همه‌چیز را باز می‌کند). نرخ را طوری بگذار که کسب امتیاز برای یک مورد جدید چند روز طول بکشد.

## ۶. پرداخت
- تأییدشده: جریان زرین‌پال شامل درخواست پرداخت و **verify** است؛ طبق مستندات زرین‌پال، اگر اعتبارسنجی خودکار در پنل غیرفعال باشد، پذیرنده باید متد verify را صدا بزند. بنابراین در هوک PocketBase باید verify صدا زده شود و تراکنش با authority یکتا idempotent باشد.
- تأییدنشده: تمدید خودکار (کسر مستقیم) ماهانه. تا بررسی مستندات، طراحی امن این است: «اشتراک ۳۰ روزه» که با پرداخت جدید تمدید می‌شود + یادآور قبل از انقضا.
- پیش از شروع: شرایط پذیرنده (تأیید کسب‌وکار، صفحه‌های قوانین/بازپرداخت/حریم خصوصی) را از خود درگاه بپرس.

## ۷. کد تخفیف و کمپین
- `coupons`: کد، نوع (درصد، مبلغ، توکن هدیه، روز آزمایشی)، بازه‌ی اعتبار، سقف کل و برای هر کاربر، طرح‌های مجاز.
- `campaigns`: بازه یا قاعده‌ی دوره‌ای (هفتگی/ماهانه) که کوپن یا قیمت ویژه را فعال می‌کند.
- تایمر کمپین باید از **زمان سرور** حساب شود (اختلاف ساعت کلاینت اصلاح شود)، وگرنه با تغییر ساعت دستگاه دور زده می‌شود.
- اعمال تخفیف و محاسبه‌ی قیمت نهایی فقط در سرور.

## ۸. خانه‌ی شبیه CrazyGames
- شبکه‌ی کاشی با **کاور** برای هر مورد، چیپ‌های دسته، جست‌وجو، بخش‌ها: «ادامه بده»، «پرطرفدار»، «جدید»، «پیشنهاد برای تو».
- یک ضربه روی کاشی ← صفحه‌ی همان بازی (توضیح، دکمه‌ی بازی، مرتبط) ← بازی. مهمان بدون ورود بازی می‌کند و بعد از اولین گزارش پیشنهاد «ذخیره‌ی پیشرفت» می‌بیند.
- کم داریم: کاور هر پکیج (SVG/WebP)، فیلد `category` و `featured`، شمارنده‌ی محبوبیت (Cloud) یا انتخاب دستی (Local).

## ۱۰. تصمیم‌های لازم از تو (قبل از ۳A)
1. ورود با ایمیل یا شماره موبایل (OTP با سرویس پیامک)؟ پیشنهاد: موبایل برای بازار ایران.
2. محدوده‌ی پولی: کل پکیج یا بخش‌به‌بخش (پیشنهاد: «پارت اول رایگان»)؟
3. عددهای اقتصاد: توکن ماهانه، هزینه‌ی هر مورد، سقف امتیاز روزانه.
